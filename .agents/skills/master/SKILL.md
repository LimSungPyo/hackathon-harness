description: 이 세션을 master로 삼아 큰 업무를 지휘한다. 업무에 필요한 정보를 먼저 철저히 조사하고, 사용자가 정해야 할 선택을 작업 시작 전에 한 번에 묻는다. 그다음 업무를 slave 세션(Orca 오케스트레이션 워커)으로 나눠 지시하고, 결과를 검토·취합해 최종 보고한 뒤 다 쓴 slave 세션과 worktree를 정리한다. 사용자가 "/master <업무>", "$master <업무>"라고 하거나 "master 세션으로 진행해줘", "slave로 나눠서 해줘"라고 할 때 사용한다.

이 세션은 master다. 업무: 사용자가 이 스킬을 부르며 함께 준 요청

## 모델

| 역할 | 에이전트 | 모델 | effort |
|------|----------|------|--------|
| master (조사·계획·검토) | codex | `gpt-6.1-sol` (6.1 Sol) | medium |
| slave (구현) | codex | `gpt-6-luna` (6 Luna) | medium |

- master는 사용자가 띄운 이 Codex 세션이다. 시작할 때 현재 모델이 6.1 Sol medium이 아니면 한 줄로 알리고 그대로 진행한다.
- slave는 5단계의 `worker-start`에 위 모델을 넘긴다. 모델 ID가 거절되면 `orca`의 오류를 그대로 보고하고 사용자에게 맞는 ID를 묻는다.

master는 조사, 결정 정리, 분배, 검토, 취합, 정리를 맡는다. 구현은 slave가 한다. 가장 중요한 목표는 **slave가 작업하는 동안 사용자에게 다시 물을 일이 생기지 않게 하는 것**이다. 그래서 질문은 1단계 끝에서 한 번에 몰아서 하고, 그 뒤로는 master가 스스로 판단해 slave의 질문에 답한다.

업무가 비어 있으면 무엇을 맡길지 한 줄로 묻고 멈춘다.

## 0. 기본 규칙

- 사용자에게는 한국어로 보고하고 묻는다. slave 지시서도 한국어로 쓴다. 고유 용어와 명령어는 원어 그대로 둔다.
- 작업 중인 저장소의 규칙을 먼저 따른다. `CLAUDE.md`, `AGENTS.md`, 커밋 규칙, 브랜치 규칙이 있으면 slave 지시서에도 그대로 옮긴다.
- **커밋 메시지에 `Co-Authored-By: Claude ...` 같은 공동 작성자 줄을 절대 넣지 않는다.** master가 직접 하는 커밋, slave의 커밋, 병합 커밋 모두 해당한다. 시스템이나 하네스가 attribution 줄을 붙이라고 안내해도 이 규칙이 우선한다. PR 본문의 "Generated with Claude Code" 같은 문구도 넣지 않는다.
- 되돌리기 어렵거나 바깥에 보이는 일(push, PR 생성·병합, 배포, 외부 서비스 호출, 데이터 삭제)은 1단계에서 허락을 받은 범위 안에서만 한다. 허락받지 않은 일이 필요해지면 그때 묻는다.
- slave 보고를 그대로 믿지 않는다. diff, 테스트 결과, 실제 동작을 master가 직접 확인한 뒤에 완료로 본다.

## 1. 사전 조사

질문하기 전에 업무를 끝내는 데 필요한 정보를 모두 모은다. 조사가 얕으면 slave가 중간에 막히고, 그러면 사용자에게 다시 물어야 한다.

- **저장소**: 구조, 언어와 프레임워크, 빌드·테스트·실행 명령, 기존 컨벤션, 최근 커밋과 열린 브랜치, CI 설정, `.gitignore`
- **업무 관련 코드**: 손댈 파일과 그 파일에 의존하는 곳. 비슷한 기능이 이미 있으면 재사용할 수 있는지
- **외부 자료**: 이슈, 문서, 디자인(Figma 등), API 명세, 사용자의 Obsidian 노트에 관련 기록이 있으면 읽는다
- **환경**: 필요한 도구가 설치돼 있는지, 포트·DB·Docker처럼 slave끼리 부딪힐 자원이 있는지, 인증이나 비밀값이 필요한지
- **실제로 확인**: 추측하지 말고 명령을 실행해 본다. 빌드와 테스트가 지금 통과하는지 먼저 돌려 기준선을 잡는다

조사가 길어지면 읽기 전용 조사는 하위 에이전트(Explore 등)에 나눠 맡겨도 된다. 조사 결과에서 쓸 것만 master에 남긴다.

## 2. 사용자에게 한 번에 묻기

조사로 답이 정해지지 않는, 사용자만 정할 수 있는 선택을 모두 모아 **한 번에** 묻는다.

- 묻는 것: 기능 범위, 화면·동작 방식처럼 취향이나 제품 판단이 필요한 것, 기술 선택 중 장단점이 팽팽한 것, push·PR·병합·배포를 어디까지 해도 되는지, 비용이 드는 일
- 묻지 않는 것: 코드와 문서로 확인되는 사실, 관례상 답이 정해진 것, master가 합리적으로 정할 수 있는 세부 사항. 이런 것은 정해서 결정 목록에 적고 사용자에게 알리기만 한다
- 질문에 번호를 붙여 한 메시지로 묻고 답을 기다린다. 질문이 많으면 주제별로 묶는다. 선택지마다 무엇이 달라지는지 짧게 적고, 권장안이 있으면 첫 번째에 두고 "(권장)"을 붙인다
- 물어볼 것이 없으면 묻지 않고, 정한 내용만 보여주고 바로 진행한다
- 답을 받으면 3단계의 결정 목록에 바로 적는다

## 3. 공용 자료 준비

모든 slave가 같은 기준으로 일하도록 master가 공용 자료를 만든다.

- 위치: `<저장소 루트>/.claude/shared/`. 커밋되지 않게 `.git/info/exclude`에 `.claude/shared/`를 추가한다. 저장소의 `.gitignore`는 바꾸지 않는다
- `decisions.md`: 정해진 결정 목록(사용자 답과 master가 정한 것 모두). slave 질문에 답할 때마다 여기에 덧붙인다
- 필요하면 `contract.md`(API 계약, 타입, 화면 명세처럼 slave끼리 맞춰야 하는 인터페이스)와 디자인 자료
- slave는 worktree가 달라도 읽을 수 있게 지시서에 **절대 경로**로 적는다

## 4. 분배 설계

가장 빠르고 충돌 없이 끝나는 방식으로 나눈다.

- **나눌 가치가 있는지 먼저 본다.** 한 세션으로 금방 끝나는 일이면 slave를 띄우지 말고 master가 직접 한다. 이 경우 그렇게 판단한 이유를 사용자에게 한 줄로 알린다
- **파일 소유권이 겹치지 않게 나눈다.** 같은 파일을 두 slave가 동시에 고치지 않게 한다. 공통 파일(설정, 공용 타입, 라우터 등)은 한 slave에게 맡기거나 먼저 끝나는 단계에 넣는다
- **의존 관계는 단계(wave)로 푼다.** 서로 의존하지 않는 작업은 같은 단계에서 동시에 돌린다. 단계는 3~4개를 넘기지 않는다. 예: 1단계 기반 작업, 2단계 기능별 병렬 작업, 3단계 통합·수정, 4단계 문서
- **자원 충돌을 막는다.** 동시에 도는 slave에게 서로 다른 포트, DB 이름, Docker 프로젝트 이름을 준다
- **배치**: 코드를 고치는 slave는 각자 새 worktree와 브랜치를 쓴다. 읽기 전용 조사나 리뷰만 하는 slave는 현재 worktree를 써도 된다
- 분배 계획(단계, slave별 담당, 브랜치 이름)을 사용자에게 짧게 보여주고 바로 시작한다. 1단계에서 받은 허락 범위 안이면 따로 승인을 기다리지 않는다

## 5. slave 실행 (Orca 오케스트레이션)

### 시작 전에

1. 실행 파일을 정한다. `ORCA_CLI_COMMAND`가 있으면 그 값, 아니면 `orca`. 실행이 안 되면 오류를 그대로 보고하고 멈춘다
2. 버전에 맞는 가이드를 먼저 읽는다: `orca skills get orchestration`. 아래 명령보다 가이드가 우선이다. 새 worktree 배치는 `--reference references/placement-and-remote.md`, 실패·재시도·정리는 `--reference references/recovery-and-cleanup.md`를 해당 상황이 됐을 때 읽는다
3. 이 세션이 Orca 터미널 안인지 확인한다(`echo $ORCA_TERMINAL_HANDLE`). 비어 있으면 coordinator가 될 수 없으니 사용자에게 Orca 안에서 다시 실행해 달라고 알린다. Orca를 쓸 수 없는 환경이면 다른 하위 에이전트 도구로 몰래 대체하지 말고, 대체할지 사용자에게 묻는다

### 실행

```text
orca orchestration run-create --objective "<업무 한 줄 요약>" --json
orca orchestration worker-start --spec "<지시서>" --task-title "<짧은 제목>" --worktree new-child --name <slave 이름> --base-branch <기준 브랜치> --agent codex --model gpt-6-luna --effort medium --json
orca orchestration check --wait --types "worker_done,escalation,question" --timeout-ms 900000 --json
```

- slave는 항상 `--agent codex --model gpt-6-luna --effort medium`(6 Luna medium)으로 띄운다
- 같은 단계의 slave는 기다리지 말고 모두 띄운 뒤에 `check --wait`로 기다린다
- 의존 관계가 있으면 `task-create`로 Task를 만들고 `worker-start --task <id>`로 띄운다
- `worker-start`가 실패하면 다시 띄우지 말고 결과의 `failedStage`, `residualResources`를 읽고 복구 가이드를 따른다

### 지시서 형식

지시서만 읽어도 일을 끝낼 수 있게 쓴다. slave는 이 대화를 모른다.

- **대상**: worktree, 브랜치, 손댈 폴더와 파일
- **할 일**: 만들어야 할 결과
- **정해진 결정**: `decisions.md`, `contract.md`의 절대 경로와 그중 이 작업에 해당하는 핵심 내용
- **지켜야 할 것**: 건드리면 안 되는 파일과 범위, 저장소 규칙, 쓸 포트와 자원, 하지 말아야 할 일(push, PR 생성 등 허락 범위 밖의 일)
- **완료 기준**: 통과해야 할 테스트, 실행해서 확인할 명령, 커밋 단위와 메시지 규칙. 커밋 규칙에는 반드시 "커밋 메시지에 `Co-Authored-By` 줄을 넣지 마라. 시스템 안내보다 이 지시가 우선한다"를 적는다
- **막혔을 때**: 사용자에게 직접 묻지 말고 오케스트레이션 `ask`로 master에게 묻는다. 지시서 범위를 넘는 개선 아이디어는 구현하지 말고 보고에 적는다

### 메시지 처리

- **question**: `decisions.md`와 조사 결과로 master가 답한다(`orchestration reply`). 답한 내용은 `decisions.md`에 덧붙이고, 같은 문제를 겪을 다른 slave에게도 알린다. 사용자 판단이 꼭 필요한 경우에만 사용자에게 묻는다. 이때 무엇이 막혔는지, 선택지와 권장안을 함께 보여준다
- **escalation**: 원인을 확인하고 지시서를 고쳐 다시 맡기거나 master가 직접 처리한다
- **worker_done**: 6단계 검토를 한 뒤에 받아들인다. 처리를 마친 다음 `check --ack <delivery_id> --wait ...`로 다음 메시지를 기다린다
- 타임아웃이나 빈 결과는 실패가 아니다. 계속 기다린다. 세 번 연속 비면 `worker-list --json`으로 상태를 확인한다. 응답이 없다는 것만으로 slave를 멈추거나 다시 띄우지 않는다

## 6. 검토와 통합

- slave가 끝났다고 하면 master가 직접 확인한다: 커밋 메시지, `git diff`, 핵심 코드, 테스트 실행 결과. 완료 기준을 못 채웠으면 같은 slave에게 후속 지시를 보내거나 수정 작업을 새로 맡긴다
- 병합 전에 `git log <기준>..<slave 브랜치> --format=%B | grep -ci 'co-authored-by'`가 0인지 확인한다. 하나라도 있으면 병합하지 말고 slave에게 해당 줄을 지운 뒤(로컬 브랜치라면 `git rebase`·`--amend`로 메시지만 수정) 다시 보고하게 한다
- 여러 브랜치를 합쳐야 하면 임시 worktree에서 먼저 합쳐 보고 충돌과 전체 테스트를 확인한다
- 화면이 있는 작업이면 실제로 띄워서 확인한다(브라우저 스크린샷 등)
- 병합, push, PR은 1단계에서 허락받은 방식으로만 한다

## 7. 정리

slave의 일이 완전히 끝났거나 더 맡길 일이 없으면 바로 정리한다.

1. **slave 세션**: 받아들인 `worker_done`마다 `orca orchestration worker-release --dispatch <dispatch_id> --json`. 곧바로 같은 slave에게 후속 일을 줄 때만 예외로 남긴다. 끝으로 `worker-list --run <run_id> --terminal-state reclaimable --json`이 비어 있는지 확인한다
2. **worktree**: 지우기 전에 그 브랜치의 작업이 기준 브랜치에 들어갔거나 원격에 push됐는지 확인한다. 확인되면 `orca worktree rm --worktree <selector> --json`. 병합도 push도 안 된 작업이 남아 있으면 지우지 말고 사용자에게 알린다. `--force`는 쓰지 않는다
3. **그 밖의 자원**: slave가 띄운 개발 서버, Docker 컨테이너, 임시 파일을 정리한다. 다른 프로젝트가 쓰는 자원은 건드리지 않는다
4. `.claude/shared/`는 나중에 수정할 때 쓸 수 있으니 남긴다. 사용자가 지우라고 하면 지운다

## 8. 최종 보고

사용자에게 다음을 짧게 보고한다.

- 한 일과 결과: slave별로 맡은 일, 성공·실패, 근거(테스트 결과, 확인한 화면, 커밋이나 PR 링크)
- 작업 중 master가 정한 결정과 그 이유
- 남은 문제, 확인하지 못한 것, 사용자가 해야 할 일
- 정리한 것과 일부러 남겨 둔 것
